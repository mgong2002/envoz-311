Overlay principles

A thin layer that behaves like a good guest

Envoz adds a voice channel and a routing brain — it never asks your staff to move into a new system.

🗄

Write into the CRM residents already know

Overlay mode creates the case in SeeClickFix, Tyler, or QAlert, so the case number a resident receives is the one your CRM issued — never a parallel record living somewhere else.

🛠

No staff workflow disruption

Cases land in the same queues, categories, and dashboards staff use today — with confidence and rationale attached — so there is no second console to check and no retraining program to fund.

📧

Structured email fallback when APIs fail

If a connector is down, Envoz sends a fully structured case packet — category, location, priority, transcript summary — to the department inbox and flags it for reconciliation when the API recovers.

🔁

Retry with idempotency

Every write carries an idempotency key, so a retry after a timeout can never create a duplicate case — and a resident can never be confirmed twice for the same report.

✓

Proof that the case number was issued

Residents only hear a case number after the system of record returns one; every confirmation links to a timestamped write receipt in the audit log.

🔒

Tenant-scoped every time

Credentials, taxonomies, GIS layers, and knowledge sources are isolated per city — Vista Robles data never grounds a Harbor Mesa answer, and no connector shares secrets across tenants.

📚

Connector library compounds city-to-city

Every deployment hardens the shared connector library — field mappings, retry behavior, vendor quirks — so the thirtieth city onboards in days, not the months the third one took.

What happens when your CRM’s API has a bad night

The write path degrades honestly: retry with idempotency, fall back to structured email, and never — under any failure — fabricate a confirmation.
